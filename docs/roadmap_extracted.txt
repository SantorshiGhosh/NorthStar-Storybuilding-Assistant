1. Product definition and vision
NorthStar is a browser-based writing environment for novelists and screenwriters. A writer can upload an existing manuscript or write in a built-in editor. The system analyzes the story and builds persistent narrative memory: characters, locations, objects, relationships, world-building rules, events, and timeline details.
As the manuscript grows, the AI compares new passages with previously established story information. It identifies possible continuity contradictions, explains why they may be conflicts, and cites the earlier and newer passages. The author remains in control: the application must never rewrite the manuscript automatically.
Core value proposition
Writers should focus on creating stories. NorthStar should remember the details and warn them when something does not add up.
Example continuity scenario
Source
Story passage
Chapter 2 — established fact
“Arin lost his left arm during the battle at Blackstone.”
Chapter 8 — new passage
“Arin lifted his left hand and opened the ancient door.”
The application should flag this as a potential continuity contradiction, show both chapter references, and suggest that the writer clarify whether Arin has a prosthetic, recovered, or whether the passage needs editing. The issue must remain subject to author review.
Primary product capabilities
Import a manuscript or write in the built-in editor.
Automatically extract characters, places, objects, relationships, facts, and events.
Maintain persistent, editable narrative memory.
Visualize story entities and relationships in an interactive knowledge graph.
Detect possible continuity conflicts with source evidence.
Track character profiles, personality signals, dialogue style, and story chronology.
Support multiple independent projects for each user.

Implementation decisions
Use PostgreSQL as the source of truth for structured narrative memory.
Use ChromaDB for semantic retrieval, not as the primary database.
Use NetworkX to build and analyze graphs from entities and relationships stored in PostgreSQL. NetworkX is a Python library, not a persistent graph database.
Start with one AI provider behind a provider-independent interface.
Avoid adding LangChain, LangGraph, Redis, Celery, or other infrastructure unless a concrete requirement justifies it.
Do not assume a free hosting tier provides durable disk storage. ChromaDB needs persistent storage; use a supported persistent volume or a fallback retrieval implementation for the demo.

5. Multi-agent AI design
Central orchestrator
The orchestrator controls task order, invokes agents, validates their outputs, handles failures, and persists results. It should enforce project boundaries and avoid letting unvalidated model output directly change the database.
Agent 1 — Narrative Extraction Agent
Extract characters, locations, objects, events, and facts.
Identify relationships between characters and other entities.
Return structured JSON validated with Pydantic.
Include chapter IDs, passage IDs, and source quotes for extracted facts.
Agent 2 — Continuity Guardian Agent
Retrieve relevant earlier story facts and passages.
Compare new content against established facts and rules.
Identify possible contradictions and explain the reasoning.
Cite the earlier and newer passages.
Classify results as likely conflict, possible conflict, intentional/explainable event, or insufficient evidence.
Agent 3 — Character Intelligence Agent
Maintain character profiles and recurring traits.
Compare dialogue samples for possible voice drift.
Track relationships and character development.
Treat voice drift as a stylistic signal, not an objective contradiction.
Agent 4 — Timeline Agent
Extract story events and temporal references.
Identify explicit dates and relative event order.
Track character locations when evidence exists.
Flag possible chronology conflicts for review.
Structured output example
{  "issue_type": "character_fact_conflict",  "severity": "high",  "confidence": 0.91,  "explanation": "The character uses an arm previously established as lost.",  "evidence": [    {"chapter": 2, "quote": "Arin lost his left arm."},    {"chapter": 8, "quote": "Arin lifted his left hand."}  ],  "suggestions": [    "Clarify whether Arin has a prosthetic.",    "Explain whether the injury was reversed."  ]}
The confidence value is a model estimate, not a calibrated probability. Validate all output against a Pydantic schema and verify that cited passages actually exist in the manuscript.

7. Manuscript processing pipeline
Format
Suggested parser

Processing stages
Validate file extension, MIME type, and size. Store the upload in a private location associated with the correct project.
Extract text while preserving chapter headings, paragraph boundaries, page numbers where available, and text offsets.
Segment the manuscript into chapters and smaller passages. Give each passage a stable ID and source location.
Send manageable chunks to the extraction agent. Ask for structured entities, relationships, events, and facts.
Save structured memory to PostgreSQL, index passages in ChromaDB, and build/update the NetworkX graph.
Run continuity checks and save the results for the frontend.
For the first version, process one manuscript sequentially. Avoid building a complex distributed background-job system unless processing time makes it necessary.
8. Continuity detection engine
The continuity engine is the central differentiator. Use a hybrid approach rather than relying on one broad LLM prompt.
Step 1 — Retrieve relevant memory
Search ChromaDB for semantically related earlier passages.
Query PostgreSQL for facts about mentioned characters, locations, objects, and rules.
Use the graph to identify related entities and relationships.
Step 2 — Run deterministic checks
Established information
New information
Possible issue
Character is dead.
Character appears alive.
Death continuity.
Character lost left arm.
Character uses left hand.
Physical continuity.
Character is in London.
Character appears in Tokyo at the same time.
Location continuity.
Event occurred in 2040.
Later passage places it in 2035.
Timeline continuity.
Rules must allow for flashbacks, dreams, unreliable narration, resurrection, prosthetics, time travel, and deliberate twists. A rule should generate a candidate issue, not automatically declare the author wrong.
Step 3 — Contextual LLM assessment
Provide the model with the new passage, relevant retrieved facts, original supporting passages, and any triggered rule. Ask it to assess whether there is a likely contradiction, possible contradiction, intentional or explainable event, or insufficient evidence.
Issue review controls
Resolved
Mark intentional
Dismiss
Review later
Never automatically rewrite the manuscript or overwrite established story facts. Any change to narrative memory should be explicitly approved by the author.

11. Security and manuscript privacy
Manuscripts may be unpublished and confidential. Privacy must be built into the storage and processing design, not added as a presentation claim.
Infrastructure security
Use private Supabase Storage buckets.
Enable Row Level Security on every project-related table.
Use HTTPS for application communication.
Validate user access to every project and manuscript operation.
Keep service-role keys and AI API keys on the backend only.
Application-level encryption
For stronger storage privacy, encrypt manuscript files before storing them using authenticated encryption such as AES-256-GCM. Keep encryption keys outside the database and source repository. A production system should use a dedicated key-management service.
Upload -> Validate -> Encrypt -> Private Storage                         |Authorized retrieval -> Decrypt for processing                         |              AI analysis / indexing                         |          Persist only necessary derived data
For the hackathon, implement private storage, RLS, HTTPS, and a tested encryption approach. If application-level encryption is included, test the full upload/decrypt/process flow. Do not claim end-to-end encryption unless the architecture genuinely provides it.
Additional privacy safeguards
Never expose Supabase service-role keys in the React application.
Never commit secrets to GitHub.
Do not log manuscript contents or encryption keys.
Isolate all database and vector searches by project ID.
Send only the relevant passages to the LLM rather than the entire manuscript where possible.
Review the selected AI provider's current retention and data-use terms. Free API access does not automatically mean that submitted content is excluded from retention or training.

17. Main risks and mitigations
Risk
Mitigation
Free AI quota exhausted
Cache analysis, use targeted requests, and keep deterministic checks as a fallback.
LLM invents facts
Require source quotes; validate structured output; verify passage references.
False continuity warnings
Combine deterministic candidate checks with contextual model review.
ChromaDB loses data
Use persistent storage or a fallback retrieval layer.
Deployment takes too long
Test deployment early rather than waiting until the end.
Large manuscripts process slowly
Limit demo manuscript size and process sequentially.
Team integration conflicts
Agree on API contracts and JSON schemas before parallel work.
Cross-project data leakage
Enforce RLS and project-level filters in every service.
Encryption breaks analysis
Test decrypt-process-re-encrypt flow before claiming encrypted processing.
Check current AI provider free-tier quotas and terms before the event. The demo should still show basic continuity checks if the external AI API becomes unavailable.

19. Success criteria and immediate next steps
Definition of success
A judge should be able to complete this workflow:
Create a project.
Upload a manuscript.
See the AI identify characters, locations, and important facts.
Explore the generated knowledge graph.
Submit new text containing a contradiction.
See the AI identify the potential issue.
Read the earlier and newer passages supporting the warning.
Decide whether the warning is intentional or should be resolved.
Immediate next steps
Create the GitHub repository.
Assign temporary roles based on team members' skills.
Create the Supabase project and configure private storage and RLS.
Agree on the database schema and API response formats.
Build the manuscript upload-to-continuity-detection workflow before expanding into advanced features.
First technical milestone
Upload a manuscript → Extract story facts → Store memory → Detect one contradiction → Return evidence.
If this workflow works reliably, the central intelligence of NorthStar is functioning. The editor, graph polish, timeline, and advanced agents can then build around it.
Final implementation principle
Do not let NorthStar become just another chatbot with a document-upload button. Its differentiator is persistent, evidence-backed narrative memory. The system should be able to explain what is known about a character, where a fact was established, what happened before an event, which story rules apply, and whether new writing conflicts with previously established information.
Build the smallest reliable version of that capability first. A stable, evidence-backed continuity demonstration is more valuable than many incomplete features.
